## 1. 認識 DevWeave

### 1.1 核心定位

DevWeave 是 repository 內建的 SDLC router。它不是 issue tracker、RAG 系統、資料庫或另一個 agent orchestrator；它的責任是把一次軟體變更拆成可追溯的 work item，保留需求、設計、任務、驗證與人工核准紀錄。

主要入口分為兩層：

| 入口 | 對象 | 用途 |
| --- | --- | --- |
| `$devweave ...` | Codex 使用者 | 以自然語言建立、推進、檢視與核准 work item。 |
| `devweave.py ...` | 維護者與自動化 | 以 UTF-8 JSON 操作 engine 的完整 machine interface。 |

公開 router 只有 DevWeave。`grill-me`、`grilling`、`codebase-design`、`diagnosing-bugs` 與 `tdd` 是階段內 companion methods，不會建立第二套 lifecycle。

### 1.2 核心流程

```text
requirements → scope_review → design → build_review
      → implementation → verification → acceptance_review → closed
```

| Gate | 審查內容 | 核准後可做的事 |
| --- | --- | --- |
| G1 / `scope` | brief、requirements、risk、scope、discovery、Wiki context | 進入設計。 |
| G2 / `build` | design、plan、DEC/TASK traceability | 依 approved scope 修改產品內容。 |
| G3 / `acceptance` | diff、驗證、evidence、baseline、Wiki、AC/TASK matrix | 核准後關閉 work item。 |

任何 gate 變成 stale，都必須回到 engine 指示的最早階段，不可手動修改 state 來跳過。

## 2. 安裝與初始化

### 2.1 前置需求

- 本次提供 0.2.2 VSIX；交付內容是 repository 與 `vscode-extension/devweave-control-center-0.2.2.vsix`，既有 0.2.1 artifact 保留，不包含 Marketplace 上架，也不承諾 macOS/Linux 支援。
- 技術門檻是 VS Code 1.90+ 與 Python 3.11+；這是安裝／執行條件，不是本次已認證組合的宣告。
- Git repository；DevWeave 會以 Git root 作為所有相對路徑的安全邊界。
- Python 3.11 或更新版本。
- Codex CLI 或 VS Code Codex Extension；公開操作需要 Codex Chat 完成 handoff。
- UTF-8 文字環境。
- Codex repository hook trust。第一次使用 `.codex/hooks.json` 時，請在 Codex 提示中信任此 repository。

DevWeave runtime 只依賴 Python standard library，不需要 `pip install`。Node.js、`npx` 與 network 只會在人工安裝或更新 companion Skills 時使用。

本次認證環境是 Windows x64 build 10.0.26200／25H2、VS Code 1.131.0、Python 3.14.6、Git 2.51.0.windows.1 與目前 Codex host；驗收基準為 Python full suite 103 項與 Extension unit tests 77 項。

### 2.1.1 安裝 Windows VSIX

1. 從 repository 取得 `vscode-extension/devweave-control-center-0.2.2.vsix`。
2. 在 VS Code 開啟 Extensions 視窗，按右上角 `...`，選擇「Install from VSIX…」，選取 VSIX 並等待安裝完成。
3. 依提示重新載入 VS Code，開啟 DevWeave repository，從 Activity Bar 開啟 DevWeave Control Center。

Windows 終端也可執行 `code --install-extension vscode-extension/devweave-control-center-0.2.2.vsix`；本 release 不會從 Marketplace 自動更新。若發生發布事故，立即停止散布並停用或解除安裝 0.2.2；這些操作不會自動刪除 `.devweave`、Wiki 或 workspace 資料。保留 workspace snapshot 與 logs，0.2.1 artifact 作為回溯參考，建立 bug work item，修復後產生新版本。

### 2.1.2 第一次開啟與初始化

第一次開啟 Control Center 時，先確認目前 workspace folder，再按「初始化 DevWeave」。Extension 會先顯示寫入範圍與不會寫入的內容，只有按「繼續初始化」才會建立固定 bootstrap bundle；按「取消」不會寫入 repository。

初始化採 non-overwrite 與 semantic adoption：合法的 evolved project、baseline 或 Wiki bytes 會顯示 adopted，既有不同內容不會被覆寫。若有 reserved path conflict、寫入失敗或使用者取消，流程會 fail closed；本次新建立的檔案會回復，既有檔案保持不變，不留下 partial control bundle。完成後依 readiness 提示信任 Codex hook、設定 verification commands，再建立第一個 work item。

### 2.2 檢查目前 repository

在 repository root 執行：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . doctor
python -B .agents/skills/devweave/scripts/devweave.py --repo . project
python -B .agents/skills/devweave/scripts/devweave.py --repo . status --all
```

`doctor` 會檢查 Python、Git、`.devweave/project.json`、DevWeave skill、Codex hook、驗證命令與 Wiki compatibility。本專案目前的 project 設定包含 `locale: zh-TW`、`schema_version: 1`、`knowledge.root: wiki` 以及 `unit-tests` 驗證命令。

### 2.3 初始化未管理 repository

若 root 沒有 `.devweave/project.json`，可執行：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . init
```

`init` 會非破壞性建立 `.devweave/project.json`、三份 baseline、work-item 目錄、cache 目錄與 root `wiki/` starter。既有相容 Wiki 會被採用且不覆寫；不相容內容會回報 `knowledge_conflict`。未初始化 repository 不會被 Codex 自動隱式啟動，請明確使用 `$devweave new`、`$devweave feature`、`$devweave refactor` 或 `$devweave bug`。

`init` 的執行順序固定為：read-only Wiki preflight → project lock 內再次 preflight → exclusive-create 缺少的 Wiki starter 與 typed directories → 建立或升級 `.devweave/project.json`、baseline、cache、work-item 目錄。非保留自訂內容（例如 `wiki/notes.md`）不會因缺少 `index.md` 而被判為 conflict；只有 reserved starter path 的錯誤 filesystem type、frontmatter 或 directory type 會回報 `knowledge_conflict`。這個 conflict 會保留所有既有 Wiki bytes，且不建立本次呼叫的 partial control bundle。

### 2.4 Hook 信任與 session binding

`.codex/hooks.json` 設定 PreToolUse hook，會檢查 `Bash`、`apply_patch`、`Edit` 與 `Write`。在 managed repository 中，可能修改狀態的操作必須屬於 active work item，且目前 session 已綁定該 work item。

通常由 Codex skill 協調 binding；若需要直接呼叫 CLI：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . bind `
  --work <work-id> --session-id $env:CODEX_THREAD_ID
```

`--session-id` 必須使用 Codex 實際提供的 session ID；若環境沒有此值，就省略該參數並讓 hook 協調 binding。若 CLI 回傳 `status: awaiting_hook`，代表 CLI 自己看不到 Codex session ID。只有 PreToolUse hook 回傳 additional context 確認 binding 時，才可視為已綁定；不要自行猜造 session ID。

## 3. 公開 Codex 對話命令

這些是使用者應優先使用的 chat surface。`next`、`status`、`approve` 等是 skill router 的對話意圖，不是每一個都對應到同名 Python CLI subcommand。

| 命令 | 用途 |
| --- | --- |
| `$devweave new <goal>` | 在新 repository 建立第一個 bounded vertical slice。 |
| `$devweave feature <request>` | 新增功能或文件能力。 |
| `$devweave refactor <target and outcome>` | 在維持可觀察行為下重構。 |
| `$devweave bug <symptom>` | 處理有 expected/actual 與重現條件的錯誤。 |
| `$devweave next [work-id]` | 依目前 phase 提供下一步與應讀的 reference。 |
| `$devweave status [work-id]` | 顯示 work、gate、task、evidence 與 Wiki health。 |
| `$devweave revise [work-id] <decision change>` | 從最早受影響 phase 重新規劃。 |
| `$devweave approve [work-id]` | 核准目前 pending gate；必須有真人明確確認。 |
| `$devweave wiki bootstrap` | 建立或續接 repository-wide Codebase Wiki bootstrap；核心 Wiki 已完整時不建立 work item。 |

### 3.1 Control Center 的 Preview 與 Codex handoff

Control Center 的公開操作不會直接執行 engine，也不會直接複製未確認的 prompt。請依序操作：選擇 work 或 task → 按「預覽公開操作」→確認「會做什麼／不會做什麼／複製後要做什麼」→按「複製 prompt」→若顯示 Plan Mode handoff，先切換 Plan Mode，再到 Codex Chat 貼上、審閱並送出→回到 Control Center 按「重新整理檔案快照」。

Preview 綁定目前 panel、操作 intent 與 snapshot revision。Refresh、切換 work、初始化結果或 workspace snapshot 更新後，舊 preview 會失效，必須重新預覽；這是刻意的安全邊界，避免把過期 prompt 複製到 Codex。若 Windows clipboard 暫時失敗，當次 preview 會保留一次重試機會，成功後才消耗。

### 3.2 Legacy `copyNextAction` 與多 work

既有 `devweave.copyNextAction` command ID 保留，但它現在只會開啟 Control Center，不再直接複製：

- 只有一個 active work 時，自動開啟該 work 的 next action preview；仍須由使用者確認後複製。
- 有多個 active work 時，必須先明確選取 work；`next` 不會猜測目標。
- 沒有 active work 時，畫面會引導建立或選取 work，不會在已有 active work 時誤導建立新 work。
- `status` 可明確查詢全部 active work，適合先盤點再選取目標。

典型的 Codex 對話順序：

```text
$devweave feature 新增 CSV 匯出能力
$devweave status <work-id>
$devweave next <work-id>
$devweave approve <work-id>       # G1 或 G2 review 後使用
$devweave next <work-id>
$devweave approve <work-id>       # G3 review 後使用
$devweave wiki bootstrap          # 可獨立建立初始核心 Wiki
```

若同時有多個 active work item，engine 會回傳 `selection_required`；先執行 `status --all`，再把 work ID 明確傳入。

## 4. 完整工作流程與三道 gate

### 4.1 建立 work item

Chat surface 會把 feature intent 路由到 engine。維護者也可直接執行：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . start `
  --kind feature `
  --title "補充文件" `
  --risk standard `
  --rationale "說明風險與相容性"
```

`start` 會建立五份 Markdown artifacts、`state.json`、`events.jsonl` 與空 evidence 目錄，並記錄 source、baseline 與 Wiki base snapshot。

### 4.2 G1：需求與範圍

G1 的工作順序：

1. 先讀 `wiki/index.md`。
2. 再讀最多五個相關 Wiki pages。
3. 對 placeholder、missing、stale 或 contradictory page 記錄 gap。
4. 只有為了補足已記錄 gap，才查看 raw source。
5. 使用 `grill-me`／`grilling` 逐題確認 material requirements；G1/G2/Gate 的正式入口是 Plan Mode。當 host 暴露 `request_user_input` 時，提供兩至三個互斥選項、推薦第一項 `(Recommended)`、說明與 host `Other` 自訂答案。普通模式在 G2 前若看不到工具，先回到 Plan Mode；只有無法切換或明確選擇相容性時才使用相同格式的 structured numbered fallback。facts 從 Wiki/source 查證，不反問使用者。
6. 將回答回流 `brief.md` 與 `requirements.md`，每題包含推薦與主要取捨，未回答前不繼續下一題。
7. 以 CLI 記錄 risk 與完整 scope。
8. 執行 `validate --gate scope`。
9. 展示問題、範圍、非目標、驗收、假設、waivers、已回答決策與未決 gap，等待明確 G1 approval。

`knowledge context` 同時保存頁面 status、內容 hash 與 source fingerprint。頁面或來源觀察改變會使相依 gate currentness 失效。`knowledge status` 若建議 bootstrap，普通 work item 仍可從 gap 做最小 source fallback；建議不會阻擋 G1。

`feature` profile 需要現況、價值、影響面、相容性與非目標；`bug` 需要 failing reproduction；`refactor` 需要 G1 前的 passing baseline；`new` 需要第一個可驗證 vertical slice。

初始 Plan Mode preflight：`new`、`feature`、`refactor`、`bug`、`wiki bootstrap` 與回到 G1/G2 的
`revise`，都必須在建立或修改 Work Item 前完成 preflight。Router 只把 host 是否暴露
`request_user_input` 視為 capability 證據；看不到時先提示切換 Plan Mode，並在 `start`、`bind`、
`revise` 或 bootstrap Work Item mutation 前停止。只有使用者明確選擇 compatibility 才能使用同一份
structured numbered fallback；取消、逾時、malformed 或 ambiguous 不會猜答案或推進 Gate。未初始化
repository 的既有 `init` startup exception 保留，但 `start` 仍受此 preflight 保護。

### 4.3 G2：設計與計畫

G2 的工作順序：

1. 重讀 approved brief 與 requirements。
2. Wiki 保持唯讀。
3. 在 Plan Mode 使用 `codebase-design` 逐題確認 material design trade-off；若 host tool 不可用，先回到 Plan Mode 或在明確相容性選擇後使用相同的 structured options fallback，並以 module、interface、seam、adapter vocabulary 比較合理選項。
4. 將回答回流 `design.md`，比較合理選項並建立 `DEC-*`。
5. 完成 `plan.md`，每個 `TASK-*` 必須 trace 到 REQ/NFR、AC 與 DEC。
6. 指定 interface、data flow、failure mode、rollback、compatibility 與 observability。
7. 執行 `validate --gate build`。
8. 展示選定/淘汰方案、介面、資料流、失敗處理、回復方式、驗證策略與 residual risk，等待明確 G2 approval。

G2 通過後 engine 會依 plan 建立 pending task ledger。G2 前不能修改產品文件、程式、測試或其他 approved scope 內容；只能修改該 work item 的 Markdown artifacts。

G1/G2 Gate 是對目前 artifacts 的 Double Check，不是重新發明需求的階段。沉默、模糊同意或
Codex 的建議不會觸發 approval；若使用者改變已核准的 requirement、design、scope 或 task，
必須使用 `revise` 回到最早受影響 phase。

### 4.4 Implementation：逐項 task

每個 task 都要遵循：

```text
task start → 最小變更 → targeted verification → task complete
```

使用 CLI 更新 task 狀態，不要在 `plan.md` 手動勾選：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . task start `
  --work <work-id> --task TASK-001
python -B .agents/skills/devweave/scripts/devweave.py --repo . task complete `
  --work <work-id> --task TASK-001 --note "完成並通過 targeted check"
```

若 task 被阻擋：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . task block `
  --work <work-id> --task TASK-001 --note "說明 blocker、原因與需要的決策"
```

Implementation 期間 `wiki/` 唯讀。若需求、設計、task 或 scope 必須改變，使用 `revise --from requirements|design|implementation`，不要直接修改 approved `plan.md`。

### 4.5 G3：驗證與驗收

所有 task completed 後 phase 進入 verification。G3 的工作順序：

1. 檢視 work item base source 到目前 HEAD 的完整 diff。
2. 以 `verify` 執行 risk profile 要求的每個 configured command。
3. 建立 acceptance、regression 或 equivalence evidence；high-risk 在 final artifacts 穩定後由既有 router 固定啟動 1 個 isolated、read-only Independent Review Agent。
4. 將 reviewer 的固定 JSON response 寫入 `.devweave/cache/incoming/<work-id>/`，透過 machine-only `review record` 產生 `kind: review` evidence；Python engine 不 spawn Agent，Extension 也不啟動 Agent。
5. `passed` 正常通過；`unavailable`／timeout／malformed fallback 與 advisory findings 是 warning；critical security、data-loss、不可回復性或 scope finding 阻擋 G3，只有具名 finding ID 的窄幅 `review-critical` waiver 可解除。
6. 確認每個 AC 與 TASK 都有 current evidence。
7. 執行 `knowledge status`，檢視 affected、covered/uncovered paths 與 bootstrap 狀態。
8. 每個新式 work item 執行 Knowledge Review，選擇 `promote` 或 `no-update` 並記錄 rationale。
9. 若 promote，宣告 1–5 個內容頁並完成 refresh/delete/scaffold/index/log/seal；若 no-update，不建立 plan 或 Wiki diff。
10. 宣告 baseline targets，或透過 CLI 記錄不需更新的理由。
11. 完成 `acceptance.md` 與 matrix，列出 reviewer result、warning、findings、report evidence/hash 與 waiver。
12. 執行 `validate --gate acceptance`，等待真人 G3 approval。
13. G3 核准後執行 `close`。

G3 不是「測試有過就完成」；它還會檢查 scope、source fingerprint、evidence freshness、baseline、Wiki promotion、log append-only 與完整 acceptance artifact。

## 5. Work kind、risk 與 scope

### 5.1 Work kind

| Kind | 使用時機 | 重要 discovery／G3 要求 |
| --- | --- | --- |
| `new` | 建立新 repository 或第一個垂直切片。 | 初始架構 baseline；current acceptance。 |
| `feature` | 新增功能、文件或相容能力。 | acceptance + regression。 |
| `refactor` | 內部重構且外部行為應維持。 | G1 baseline；equivalence + regression。 |
| `bug` | 修正已觀察到的錯誤。 | G1 failing reproduction；G3 regression。 |

### 5.2 Risk level

| Risk | 定義 |
| --- | --- |
| `low` | 隔離、可逆、相容、充分測試，且沒有 security、migration 或 public-contract impact；需 downgrade rationale。 |
| `standard` | 一般變更的預設等級。 |
| `high` | authentication、security、privacy、destructive data、public contract、多服務、弱測試基線或難以 rollback。 |

High risk 不會移除 gate，而是增加 high-risk design analysis 與 current independent review。Risk 降級必須保留明確 downgrade rationale。

### 5.3 Scope

`scope` 是完整取代操作；同一次 CLI 呼叫要重複所有 `--path`：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . scope `
  --work <work-id> `
  --path README.md `
  --path docs/使用手冊.md `
  --rationale "只更新使用者文件"
```

Scope path 可是 repo-relative path 或 glob。G3 若發現 scope 外變更，必須移除變更、修正 scope 並重新走 gate，或留下明確且窄幅的 `out-of-scope` waiver。

## 6. Machine CLI 參考

### 6.1 共通規則

所有 CLI 命令從 repository root 執行：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . <command>
```

`--repo` 可指定 repository 內的任意路徑；engine 會尋找 Git root。`--json` 為相容參數，輸出本來就永遠是 JSON。CLI 不透過 shell 解析 configured command，command 的 `argv` 會以 string array 儲存並使用 `shell=false` 執行。

### 6.2 Project 與 work lifecycle

| 命令 | 主要參數 | 用途 |
| --- | --- | --- |
| `init` | 無 | 建立或補齊 project、baseline 與 Wiki starter。 |
| `start` | `--kind`、`--title`、`--risk`、`--rationale` | 建立 work item。 |
| `status` | `--work`、`--all`、`--include-closed` | 讀取 work、gate、task、evidence 與 knowledge health。 |
| `instructions` | `--work` | 回傳目前 phase、reference、pending gate 與 next action。 |
| `validate` | `--work`、`--gate`、`--include-closed` | 驗證 scope、build 或 acceptance。 |
| `bind` | `--work`、`--session-id` | 綁定 Codex session；通常交給 hook。 |
| `approve` | `--work`、`--gate`、`--actor` | 核准目前 gate。 |
| `revise` | `--work`、`--from`、`--reason` | 使受影響 gate/evidence stale 並回到指定 phase。 |
| `close` | `--work` | 在 current G3 approval 下關閉 work item。 |

建立 work item：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . start `
  --kind feature --title "新增能力" --risk standard `
  --rationale "說明風險"
```

檢視流程：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . status --all
python -B .agents/skills/devweave/scripts/devweave.py --repo . instructions --work <work-id>
python -B .agents/skills/devweave/scripts/devweave.py --repo . validate --work <work-id> --gate scope
```

### 6.3 Risk、scope 與 baseline

設定 risk：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . risk `
  --work <work-id> --level standard --rationale "標準風險"
```

若降低 risk level，另外提供 `--downgrade-rationale`。設定 scope 會取代整個 scope set；設定 baseline 更新 targets：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . baseline `
  --work <work-id> --target .devweave/baseline/architecture.md `
  --rationale "記錄接受的架構變更"
```

若沒有 baseline 變更，在 verification 以空 targets 與明確理由記錄；不要手動修改 baseline 或 state。

### 6.4 Knowledge CLI

建立或續接全 repository Wiki bootstrap（不接受 scope）：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . knowledge bootstrap
```

回傳 action 為 `created`、`resume` 或 `already_complete`；前兩者使用一般 G1/G2/G3 work item。

查看 Wiki health：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . knowledge status --work <work-id>
```

記錄 G1 context；`--page` 順序必須是 `wiki/index.md` 第一個，最多五個相關頁面：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . knowledge context `
  --work <work-id> --page wiki/index.md --page wiki/overview.md `
  --gap "overview 仍為 placeholder，需要 raw-source follow-up"
```

verification 先完成 Knowledge Review：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . knowledge review `
  --work <work-id> --disposition promote `
  --rationale "本次變更形成可跨工作項重用的 module knowledge"
```

`disposition` 可為 `promote` 或 `no-update`。`no-update` 需要非空理由，且只允許非 bootstrap、沒有 affected page、沒有 Wiki diff 的 work；不得建立 plan。產品 source fingerprint 改變後 review 與 plan 都會失效。

選擇 promote 後，在一次 `knowledge plan` 中提供完整 upsert/delete set，內容頁合計 1–5 個：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . knowledge plan `
  --work <work-id> --upsert wiki/modules/runtime.md `
  --delete wiki/modules/obsolete.md `
  --rationale "刷新受本次 source 變更影響的頁面"
```

對 plan 中尚不存在的新 upsert，可從九種 canonical template 建立 no-overwrite placeholder：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . knowledge scaffold `
  --work <work-id> --page wiki/modules/runtime.md --type module `
  --title "Runtime Module" --source src/runtime
```

支援 `overview|architecture|module|entity|pattern|dependency|decision|guide|synthesis`。`dependency` 額外必填 `--package-name`、`--version`；`decision` 額外必填 `--decision-date` 與 `--decision-status proposed|accepted|deprecated|superseded`。Scaffold 後要替換模板內容並將 status 改為 `active`。

任何內容 target 都會自動 coupled `wiki/index.md` 與 `wiki/log.md`。完成更新後封存：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . knowledge seal `
  --work <work-id> --page wiki/modules/runtime.md `
  --page wiki/index.md --page wiki/log.md
```

`knowledge seal` 會拒絕 placeholder、未替換 template token、critical lint 或無效 source。G2 與 implementation 絕對不寫 Wiki。

### 6.5 Task、evidence 與 verification

Task 狀態只能由 CLI 更新：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . task start --work <work-id> --task TASK-001
python -B .agents/skills/devweave/scripts/devweave.py --repo . task complete --work <work-id> --task TASK-001 --note "完成 targeted check"
python -B .agents/skills/devweave/scripts/devweave.py --repo . task block --work <work-id> --task TASK-001 --note "說明 blocker"
```

手動加入一般 evidence：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . evidence add `
  --work <work-id> --kind acceptance --status passed `
  --summary "完成驗收" --covers AC-001 --task TASK-001 `
  --binds-current-source
```

High-risk G3 的 Independent Review 不得用 `evidence add --kind review` 模擬。既有 router 將 reviewer 固定 JSON 寫入 incoming cache 後，使用 machine-only 介面：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . review record `
  --work <work-id> --reviewer-id <opaque-agent-id> `
  --report-file .devweave/cache/incoming/<work-id>/<attempt>.json
```

Report 必須包含 `result: passed|unavailable|critical`、`severity: none|advisory|critical`、summary、目前 `source_fingerprint`、AC/TASK coverage，以及具名 findings。Engine 會檢查 path containment、大小、格式、secret redaction、report hash 與 provenance，並將完整 redacted report 保存至 `.devweave/cache/logs/<work-id>/`。

執行 project 中設定的驗證命令並保存 raw log：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . verify `
  --work <work-id> --command unit-tests --kind regression `
  --covers AC-001 --covers AC-007 --task TASK-004 --expect zero
```

`verify` 的 `--expect` 可為 `zero`、`nonzero` 或 `any`；預設為 `zero`。verification output 會保存為 `.devweave/cache/logs/<work-id>/<EVID-id>.log`，raw log 受 project policy 限制且不應加入 Git。

### 6.6 Waiver、approve 與 close

只能對明確窄幅的阻礙建立 waiver：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . waiver add `
  --work <work-id> --kind missing-command --target unit-tests `
  --reason "說明為何無法執行及替代驗證" --gate acceptance
```

常見 waiver kind 包含 `unreproducible`、`missing-command` 與 `out-of-scope`。Critical Independent Review 只允許 acceptance gate 的 `review-critical` waiver，target 必須是單一具名 `F-###` finding ID；wildcard 或 broad waiver 會被拒絕。Waiver 不是跳過設計、驗證或人工核准的通用開關。

核准目前 gate 與關閉：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . approve --work <work-id> --gate scope
python -B .agents/skills/devweave/scripts/devweave.py --repo . approve --work <work-id> --gate build
python -B .agents/skills/devweave/scripts/devweave.py --repo . approve --work <work-id> --gate acceptance
python -B .agents/skills/devweave/scripts/devweave.py --repo . close --work <work-id>
```

`approve` 只允許目前 phase 的 gate；`close` 需要 current G3 acceptance fingerprint。Closed work item 保留在 repository 中，不能重新開啟；後續變更要建立新的 work item。

查看現有 commands：


加入或取代 configured command：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . command set `
```

| Exit code | 意義 |
| --- | --- |
| `0` | 成功。 |
| `2` | usage error 或 validation failure。 |

## 7. Artifacts、state 與 fingerprints

### 7.1 Work item 內容

每個 work item 位於 `.devweave/work-items/<work-id>/`：

| 檔案 | 責任 |
| --- | --- |
| `brief.md` | 問題、目標、使用者、範圍、非目標與風險。 |
| `requirements.md` | `REQ-*`、`NFR-*` 與 `AC-*`。 |
| `design.md` | `DEC-*`、interface、data flow、failure mode 與 rollback。 |
| `plan.md` | immutable `TASK-*` 定義與 verification strategy。 |
| `acceptance.md` | G3 的 AC/TASK/evidence matrix、結果與 residual risk。 |
| `state.json` | engine-owned machine state；禁止手動編輯。 |
| `events.jsonl` | append-only lifecycle event；禁止手動編輯。 |
| `evidence/*.json` | engine-owned evidence summary；禁止手動編輯。 |

人類可編輯的是五份 Markdown artifacts 與 approved scope 內的產品檔案；machine state 必須透過 CLI 更新。

### 7.2 Fingerprint 與 stale 行為

| 變化 | 影響 |
| --- | --- |
| G1 brief、requirements、risk、scope 或 context | G1、G2、G3 全部 stale，回到 requirements。 |
| G2 design、plan 或 build waiver | G2、G3 stale，回到 design。 |
| implementation 後 product source | source-bound evidence、Knowledge Review 與 knowledge plan stale，G3 stale，回到 verification。 |
| acceptance、evidence、baseline、G3 waiver | G3 stale。 |
| Wiki-only change | product evidence 可保持 current，但 G3 knowledge fingerprint stale。 |
| work 已 closed | 不能 reopen；建立新 work item。 |

三個 fingerprint domain 分開計算：product source、living baseline 與 Wiki knowledge。這避免單純刷新 Wiki 就讓不相關的產品測試 evidence 失效。

## 8. Wiki-first 與知識生命週期

### 8.1 Wiki 結構

`init` 或 `start` 會確保 root `wiki/` 包含：

```text
wiki/index.md                    G1 固定第一個讀取頁面
wiki/overview.md                 codebase overview starter
wiki/log.md                      append-only promotion log
wiki/architecture/               architecture pages
wiki/modules/                    module pages
wiki/entities/                   entity pages
wiki/patterns/                   pattern pages
wiki/decisions/                  decision pages
wiki/dependencies/               dependency pages
wiki/guides/                     guide pages
wiki/synthesis/                  synthesis pages
```

支援的 page type 是 `overview`、`architecture`、`module`、`entity`、`pattern`、`decision`、`dependency`、`guide`、`synthesis`、`index` 與 `log`。一般 page 必須位於對應 typed directory。

### 8.2 Frontmatter 與 source provenance

每個 Wiki page 必須有 `title`、`type`、`sources`、`last_updated`、`tags` 與 `status`；有來源的 page 還會有 `source_fingerprint` 與 `verified_by`。一頁最多五個 repo-relative sources，不能指向 `wiki/`、`.devweave/`、`.git/`、repository 外或經 symlink escape 的路徑。

source fingerprint 使用 current bytes；directory 會展開 Git tracked 與 non-ignored untracked files。dirty content、rename、delete 或 directory membership 變化會使 page stale。

### 8.3 Codebase Wiki bootstrap

`$devweave wiki bootstrap` 內部路由到 `knowledge bootstrap`。它沒有子路徑模式，而是評估整個 repository：

- 核心 overview、architecture 與 module 都是 active、sourced、current、sealed 時回傳 `already_complete`，不建立 work item。
- 若已有 active bootstrap work item，回傳 `resume`。
- 否則建立一般 `kind: feature` 且 `knowledge_profile: bootstrap` 的 work item，沿用 session binding 與 G1/G2/G3。
- G2 選定 3–5 個內容頁；G3 最少完成 overview、一個 architecture 與一個 module，最多再加兩個有證據的高價值主題。
- Bootstrap 不可修改產品 source、不可 `no-update`、不可 delete。

尚未 bootstrap 只會出現在 recommendation，不會阻擋一般 work item。

### 8.4 G1 context

`knowledge context` 是 replace operation，完整讀取順序要在同一次呼叫提供：

```powershell
python -B .agents/skills/devweave/scripts/devweave.py --repo . knowledge context `
  --work <work-id> --page wiki/index.md --page wiki/overview.md `
  --gap "overview 是 placeholder，需要回溯 raw source"
```

`wiki/index.md` 必須第一個且只出現一次；相關 pages 最多五個。Context 保存 path、status、內容 hash、stored 與 observed source fingerprint。Raw source 不是例外捷徑；missing、placeholder、stale、contradictory 或 insufficient knowledge 必須先留下 gap，然後只讀最小必要 source range。輸出應區分 Wiki facts、source-backed facts、inference 與 gaps。

### 8.5 Knowledge Review 與 verification promotion

每個新式 work item 在 G3 前都要做 Knowledge Review；這才是「每個 Work Item 更新 Wiki」的定義，不代表每次強迫產生 Wiki diff。

- `promote`：有 durable reusable knowledge。建立 1–5 個內容 targets 的 plan；Affected page 必須刷新並 seal 或宣告刪除，uncovered durable changes 可由一頁或多頁涵蓋。
- `no-update`：只允許非 bootstrap、沒有 affected page、沒有 Wiki diff，並記錄 non-empty rationale；不得建立 plan。

新頁先以 canonical scaffold 建立 placeholder，完成內容後設為 active。只要有 content target，就必須同時更新並 seal `wiki/index.md` 與 `wiki/log.md`；log 必須保留既有 body 並 append 恰好一個包含 work ID 的 `promote` heading。每個 work item 的 upsert/delete 合計最多五頁，index/log 不計入。

Wiki 是可重建的知識快取；source 與核准 artifacts 才是最終事實來源。本版本不導入 vector database、全文索引或精確 Token 計量。

## 9. Hook 與寫入安全邊界

### 9.1 PreToolUse guard

Hook 會把以下情況視為不同權限：

- Git、rg、Get-Content、status、diff 等 read-only 操作可在未 binding 時執行。
- configured verification command 仍需 active work 與 binding。
- G2 前只允許修改 current work item 的五份 Markdown artifacts。
- G2 後只允許 approved scope 內的產品檔案。
- baseline 只在 verification／acceptance 階段可寫。
- Wiki 只在 verification／acceptance 且 path 已列入 knowledge plan 時可寫；coupled index/log 自動納入允許清單。
- shell command 若提及 Wiki path，不能用來繞過精確 path 檢查；請使用 patch/edit/write 或 knowledge CLI。

Windows 0.2.2 的標準 hook command 是 `powershell.exe -NoLogo -NoProfile -NonInteractive -Command "python.exe -X utf8 -B (Join-Path (git rev-parse --show-toplevel) '.agents\\skills\\devweave\\scripts\\guard.py')"`。它可由 Codex 的 `cmd.exe` 或 PowerShell 外層啟動，並由 `guard.py` 以 UTF-8 bytes 讀寫 hook JSON；不依賴會被多層 shell 展開的 `$repo`，也不使用 `commandWindows`。若看到 `PreToolUse hook (failed)` 或 `hook exited with code 1`，代表 launcher/process 沒有正常啟動；若 hook 正常完成但操作不被允許，則會收到 DevWeave 的 JSON `permissionDecision: deny` 與具體原因。兩者不是同一種錯誤。

### 9.2 Hook 的限制

Hook 是 Codex guardrail，不是 Windows 或 Linux 的 OS sandbox。外部 editor、停用 hook 或未經 Codex 的寫入可能先發生，G3 會透過完整 Git diff、fingerprint 與 Wiki lint 重新檢查。

Bootstrap control files 使用 exact policy；Extension 不會靜默覆寫既有 `.codex/hooks.json`。更新既有 workspace 時，請在確認衝突內容後重新套用修正的 hook，並重新啟動／信任 repository hook。

## 12. 故障排除

| 症狀 | 原因與處理 |
| --- | --- |
| `No eligible DevWeave work item exists` | 尚未建立 work item；使用 `$devweave feature` 或 `start`。 |
| `selection_required` | 有多個 active work；先 `status --all`，再指定 `--work <work-id>`。 |
| `awaiting_hook` | CLI 看不到 session ID；確認 Codex 信任 hook，等待 additional context，不要猜造 ID。 |
| 寫入被拒絕且提示 G2 | 尚未通過 build gate；只能修改 work item artifacts，先完成 design 並取得 G2。 |
| 寫入被拒絕且提示 scope | 目標不在 approved scope；移除變更或使用 `revise` 重新規劃。 |
| `stale` gate 或 evidence | approved material、source、Wiki、baseline 或 acceptance 改變；執行 `status`／`instructions`，依 engine 指示回到最早 phase。 |
| `knowledge_conflict` | Wiki 有不相容非空內容；保留使用者內容，先由 maintainer 處理衝突，不要覆寫。 |
| Wiki health 為 `warning` | 常見原因是 starter placeholder、stale、orphan 或未 seal；受影響 page 需在 G3 處理，無關 warning 可記錄。 |
| `missing-command` | project verification profile 找不到必要 command；用 `command set` 補齊，或建立窄幅 acceptance waiver。 |
| verification timeout | 檢查 `.devweave/cache/logs/<work-id>/`、提高 command timeout 或縮小 targeted command；不要把 timeout 當成成功。 |
| 測試失敗 | 保留 failed evidence，定位實際問題；若需求或設計需改變，使用 `revise`。 |
| `Cannot close` | G3 尚未 current、evidence stale、acceptance 未核准或 scope／Wiki／baseline 未通過；先 `validate --gate acceptance`。 |

### 12.1 常見 JSON 錯誤欄位

CLI error 通常包含：

```json
{
  "ok": false,
  "error": {
    "code": "validation_failed",
    "message": "說明",
    "details": {}
  }
}
```

不要只看 shell exit code；同時讀 `error.code`、`details`、`validation.errors` 或 `evidence.execution_error`。
